# Development instructions

- Product name: Ironpath. Tagline: Your path to endgame PvM. Repository: PetterHL/ironpath.

- Keep code, UI text, documentation, commit messages and future implementation briefs in English. Discussion with Petter may be Norwegian.
- Read README.md, docs/DESIGN.md and the active task in TASKS.md. Consult docs/RESEARCH.md for historical evidence; the newer design controls product scope. Do not expand the scope because an API or guide exists.
- Approved direction (12 October 2026): an automatic, account-aware Ironman PvM upgrade advisor. Explain which upgrades are worth pursuing, their personal value and how to obtain them. Equipment, relevant prayers, skill levels and permanent unlocks are eligible outcomes. The primary experience must work without a goal.
- P1–P3 are implemented on PR #5, not assumed merged into main. The next assignment is **P4a, the upgrade-first vertical slice**; P4b expansion follows after review. The old 35–45-decision catalogue-first assignment is superseded. Verify current branch/PR state; reuse the latest implementation and updated documentation together. Never merge, close or reset existing PRs automatically.
- Preserve useful broad PvM content, stable identifiers, historical evidence and pending validation records. Historical T1–T4 and P1–P3 briefs describe earlier deliveries, not active requirements. The old CoX trial does not block development; fix concrete defects when found. TASKS.md remains the only backlog.
- Build this as an independent project. Iron Compass is an optional reference with overlapping features, not a required comparison gate or grounds for redirecting the work upstream. Validate our own usefulness and usability.
- Use the official RuneLite Java plugin template and current supported public APIs. Keep one Gradle project and minimal dependencies. Do not build a web app, backend, database, AI integration or general-purpose rule engine.
- Treat game state as partial observations. Unknown is not false or zero. Preserve observation time and provenance. Bank ownership, collection history and permanent unlocks are different facts.
- Keep raw account observations in memory. Persist only necessary preferences/manual confirmations in a plugin-owned local file using RuneLite's supported file API. Do not put bank data or account facts in potentially synced configuration.
- Clear account state on logout, profile/account changes and unsupported worlds. Verify character identity before applying asynchronous results. Never log bank dumps or account identifiers.
- Separate hard game requirements from recommendations. No mandatory Bowfa route, inferred player skill, invented DPS percentages, exact grind times or RNG completion percentages.
- Ship only reviewed knowledge with source references, review dates and explicit alternatives. New content and source changes are candidates, not automatically accepted facts.
- Keep evaluation pure and deterministic. Test meaningful recommendation and account-isolation failures, not getters or implementation structure.
- Reuse AccountSnapshotReader, immutable observations, Advisor, KnowledgeCatalog, the existing Swing sidebar and isolated local Filepath preferences. Extend only what actual slice cases require; no rewrite, general progression engine or universal loadout optimiser.
- Distinguish an upgrade/outcome, its acquisition routes and its contextual benefits/comparisons. Keep hard access, suggested preparation, ownership, usability and completion separate. Preserve bounded ALL/ANY semantics; an activity must not require its own reward to enter.
- Unknown ownership is not absence. Allow clearly labelled provisional upgrade cards when supported account evidence establishes potential relevance; name the unknown and offer a targeted confirmation. Never claim a missing item or available route without evidence. If relevance itself is unsupported, explain coverage rather than invent advice.
- Compare supported owned alternatives before recommending a grind; preserve specialist value when a stronger general weapon is owned. Never rank by missing-item status, goal count or a universal efficiency score. Optional goals refine relevant advice; they do not establish value or readiness.
- Show useful inaccessible upgrades with their nearest meaningful prerequisite or route check, even without a goal. Activity skips exclude acquisition routes, not owned reward utility. Group shared acquisition opportunities without summing unrelated performance gains or assuming rewards arrive together.
- Use compact single-column upgrade cards in RuneLite's narrow sidebar. Put observations, diagnostics, manual confirmations and goals behind secondary controls. Keep owned-scroll/assembly reminders in a separate quick-actions area so they do not crowd out substantial upgrades.
- Numerical claims must follow docs/DESIGN.md's comparison contract: equipment/variants, skills, prayers, boosts, style, target/phase, assumptions, model version and evidence. Propose a supported reference setup automatically and allow lightweight correction. Unsupported inputs must return an explicit unavailable/conditional result, never silently become zero.
- P4a uses a small independently authored local powered-magic model. Existing calculators are validation references, not approved dependencies or code/data imports. Check compatibility and licences before future reuse; do not relabel GPL-derived work as BSD. No runtime calculator calls or account-data export.
- Distinguish max hit, hit chance and theoretical DPS from expected target kill time and full-encounter completion time. Do not infer kills per trip, faster completions, extra deep delves or RNG progress from theoretical DPS. Effort labels must state assumptions.
- Keep derived reference setups in memory alongside observations. Invalidate confirmations after relevant input changes and clear them on account/profile/lifecycle transitions. Preserve delayed UI/IO identity guards and explicit migration or retirement of preference keys. Manual ownership never proves charged/usable gear.
- Preserve relevant regressions. Replace only assertions for deliberately superseded behaviour (goal-count ranking or always-empty provisional advice), with stronger product checks. Run required build/checks; report exact calculation boundaries and real-client tests not performed. Plugin Hub publication still requires explicit authorisation.
- Follow current Plugin Hub policy. No gameplay automation, combat instructions, reflection, subprocesses, arbitrary downloaded code or runtime guide scraping.
- Preserve third-party notices. Do not copy guides, datasets or code based solely on public availability or attribution.
- Report what changed, what was tested and what still needs in-game validation. Update only the active task's status. Do not claim Hub approval or live testing without evidence.
